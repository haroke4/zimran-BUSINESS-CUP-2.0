# FRAMEBREAK asset lab

## StoryFork scene preview

Run `npm --prefix hypothesis-non-production/test run server` and `npm --prefix hypothesis-non-production/test run dev -- --host 127.0.0.1` from the repository root, then open [StoryFork](http://127.0.0.1:5173/storyfork/). The page opens with a saved example. StoryFork defaults to `gemini-3.1-flash-lite` and reads the first key from `GEMINI_API_KEY` or `LLM_API_KEY` in `hypothesis-non-production/test/.env`. Set `GEMINI_API_KEY_SECONDARY` to rotate keys on HTTP 429. Set `STORYFORK_MODEL` to select another compatible Gemini model.

The first model call turns the brief into an art direction and a beat. Code filters and ranks the [StoryFork catalog](../../assets/storyfork/manifest.json) by setting and role. The second call selects art, visual states and composition. Code resolves lighting variants, anchors and draw order. The preview shows each selection and reports generation time and missing art. The JSON download carries the compiled scene and its diagnostics.

The custom-prop checkbox lets the compositor choose one bounded shape for a missing focal object during the same call. The available shapes cover cases, terminals, signs and dials. The preview renders a single environment shot. Episode choices and persistent interactive prop state are handled by the separate episode demo.

## Decision

Build locations from modular pieces. Keep two model calls: a story writer and a compositor. Put search, physical rules, playback and persistent state in application code. Use a versioned JSON catalog and SVG art. Start with tags, keyword match and a small alias list. Add embeddings only if they recover enough of the misses on your actual art library.

The existing Phaser corridor demo and its package files were left alone. This lab uses its installed Phaser and Vite.

## How the system works

1. **The writer plans the beat.** Give it player preferences, the current location, exact story facts, a short recap, and a small vocabulary of actions the engine can stage. It asks for things like a wet city street, low residential buildings and an openable cabinet. It supplies two choices with typed effects. For a known place it refers to the location and existing prop IDs.
2. **Code narrows the catalog.** Look up existing objects by ID. For new objects, filter by category, style compatibility, required capability and any actual constraints. Rank by tags, words and common synonyms. Send about four compact cards per requested role. A card carries the asset ID, layer, tags and needed capabilities. Leave URLs, textures and frame lists in the manifest. If an optional decoration has no match, skip it. If a story-critical prop has no compatible match, ask the writer to change the beat.
3. **The compositor builds the location and stages the beat.** Send the current beat, candidates, legal slots, current object states, and relevant clip IDs. For a new location it can decide between a skyline of towers, a row of houses, or no buildings in a different stage family. It picks where objects go and how the character approaches. Style packs share palette, perspective, scale and layer rules. They contain interchangeable pieces. Give the result a location ID and save it on first visit. On return, load the saved placements and current states.
4. **The engine checks and plays it.** Check IDs, layers, space for interactive props, anchors, legal state transitions, and timing. Fill obvious defaults in code. Phaser loads the referenced art and plays authored clips. With background generation later, both draft branches start from the same story revision, and only the chosen result advances it.

Prompts and the two real calls are in [scene.mjs](scene.mjs) and [try-model.mjs](try-model.mjs). Keep the writer's instructions about choices, causality and visible events. Keep the compositor's instructions about layout, staging and supported actions. JSON schema can restrict asset IDs and allowed values. Code still checks whether the action makes sense in the scene. [Structured output](https://aistudio.google.com/docs/structured-output)

## Adding art without growing the engine

| Asset | Authoring format | Runtime contract |
|---|---|---|
| Sky, terrain, tall house, row houses, puddle | SVG drawn by hand or generated by a coding assistant | ID, style tags, layer, size and origin. Billboards and buildings can overlap visually in the skyline. Interactive foreground needs clearance. |
| Cabinet, door, switch | SVG parts and JSON states | A default state, supported transitions, approach/handle anchors and a duration. Put the clip and SFX cue on the transition once the action needs a synced sound. |
| Stickman rig | Shared Phaser drawing rig and authored clips | Map actions such as walk, run, jump and fly to clips the rig supports. Movement declares speed and destination. A terminal animation such as die also changes character state in the story. |
| Drawn effects or elaborate motion | PNG/WebP sprite atlas plus frame metadata where it earns its keep | Same semantic clip IDs. Phaser has frame playback and an asset pack loader. Spine or Rive is worth testing if you outgrow shared rig clips. |

One manifest per art pack is enough for the team. Use a coding-assistant prompt or skill when **authoring** to enforce palette, perspective, file format, stable IDs and manifest fields. At runtime use the catalog and the selector in ordinary code. Adding another cabinet variant should be one art and data change. An entirely new interaction, for example a ladder that connects two walkable levels, is a new engine capability. Share that implementation across ladder variants. Pin asset versions used by saved episodes.

The catalog distinguishes the reusable asset `street_cabinet` from a placed object like `cache` in `rainy-crossing`. The same asset elsewhere can be closed. When the hero opens `cache`, the player computes an approach target, moves the hand to the handle, starts the door transition at contact, and commits `open` when the clip completes. Later `close` is legal. A second `open` from the same state is rejected. The lab tests this with a shared rig and a two-piece cabinet. ## What the experiments showed

| Experiment | Result | Decision |
|---|---|---|
| Catalog dump vs filtered search | 10,000 synthetic metadata records were 1,397,861 JSON bytes. Four candidates averaged 439–440 bytes **per requested role**. Direct keyword ranking found a labeled match in its top four on 14/16 answerable queries. Adding aliases reached 15/16. Local Apple embeddings and keyword + embedding fusion also reached 15/16. All filtered methods rejected 2/2 impossible requests and yielded zero incompatible candidates. | Use tags + keywords + aliases. Check ranked matches on real art packs before adding vector search. Filtered ranking was roughly 10 ms p95 or lower in this small local run. That excludes embedding construction and inference. |
| Model writes a free placement list | The local model gave the ground an invalid slot on both attempts. A first move to typed layer slots still allowed too many objects and failed twice. | Make required placements and budgets valid by construction. The final schema forced a center building, reserved space for the cabinet and bounded optional slot choices. |
| Model chooses legal slots | Three local Qwen runs with two calls each produced a wet city, a dry low-rise block and a pine trail with no buildings. Final runs took 3.41 s, 3.18 s and 3.24 s on this Mac, including both calls. The model also selected run vs walk. Chrome verified the clips, cabinet contact and open/close, revisits, reload, and layout at 390 px. | Keep two calls and a deterministic compiler. The sample covers three short layouts, two style packs and one scripted interaction type. The lab loads its small pack up front and plays saved layouts with local state. It does not implement live app integration, server storage or production latency measurements. |
| SVG vs PNG vs lossless WebP | Twelve vector pieces totaled 3,485 B as gzipped SVG, 78,457 B as PNG, and 64,140 B as lossless WebP. PNG and WebP decoded identically. A single WebP atlas was 68,224 B and used 15.4% more nominal decoded RGBA than the separate textures in this pack. | Start with SVG for this art style. It rasterizes in Phaser. Test raster atlases by pack when requests or device profiling give a reason to batch. The atlas figures omit frame metadata and GPU overhead. |

The retrieval set contains only 77 distinct texts across catalog and queries. The small model also tended to fill slots with repeats, so artists should judge variety and scene readability using larger real packs. Run a labeled catalog test on real art and measure inference and playback on a phone. Start with SQL full-text indexing once the catalog needs database indexing. Test hybrid search later on natural-language misses. [PostgreSQL full-text search](https://www.postgresql.org/docs/current/textsearch-tables.html) · [Apple sentence embeddings](https://developer.apple.com/documentation/naturallanguage/finding-similarities-between-pieces-of-text) · [pgvector hybrid search](https://github.com/pgvector/pgvector#hybrid-search) · [Qwen model card](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF)

## Five minutes, sixty minutes and part two

At 30 seconds per scene, five minutes is **10 scenes** and sixty minutes is **120 scenes**, before decision time and loading. Save exact world state and a scene/choice log in PostgreSQL. The writer gets live facts about active characters, the current place, ownership, who knows what and unresolved story threads, plus the last three scenes and one short recap. At a chapter break, start with a checkpoint every 20 scenes. At the part boundary produce a short handoff with what changed, current goals and unresolved threads. Carry exact state and saved locations into part two. Older facts are still available by entity ID. The compositor receives only the scene and staging context.

| Playback | Final memory sent as full log | Final bounded memory | Est. LLM spend, chosen branch | Est. LLM spend, both branches prefetched |
|---|---:|---:|---:|---:|
| 5 min, 10 scenes | 3,827 B | 1,554 B | $0.032 | $0.062 |
| 60 min, 120 scenes | 44,148 B | 1,571 B | $0.389 | $0.774 |

The synthetic replay recovered a locker state set in scene 2, preserved different knowledge for two characters, updated who held a key and resumed at scene 121. It rejected a stale unchosen branch. It used fixture-supplied fact IDs and measures JSON bytes. The estimates assume both model calls total 3,300 input and 900 billed output tokens per candidate scene on Gemini 3.5 Flash-Lite Standard. They exclude repairs, summaries, media and hosting. Full prefetch requires up to 478 calls for a 120-scene part, so test on-demand generation first and use one-scene prefetch where waiting actually hurts. There was no live 120-scene narrative or phone performance test. ## Reproduce

From the repository root:

```sh
npm --prefix hypothesis-non-production/test ci
npm --prefix hypothesis-non-production/test run server
npm --prefix hypothesis-non-production/test run dev -- --host 127.0.0.1
```

Copy `.env.example` to `.env` inside `test` and set `LLM_PROVIDER`, `LLM_MODEL`,
`LLM_API_KEY` and, for OpenAI-compatible servers, `LLM_BASE_URL`. The live episode
uses this single adapter, so switching models does not require changing scene code.

Open [the asset lab](http://127.0.0.1:5173/asset-hypotheses/) and switch between the three model-composed locations. The lab plays the saved model outputs and needs no API key. The production build command is `cd test && npm exec -- vite build asset-hypotheses`.

```sh
node hypothesis-non-production/test/asset-hypotheses/check-scenes.mjs
node hypothesis-non-production/test/asset-hypotheses/benchmark-retrieval.mjs
node hypothesis-non-production/test/asset-hypotheses/benchmark-retrieval.mjs --semantic
node hypothesis-non-production/test/asset-hypotheses/benchmark-textures.mjs
node hypothesis-non-production/test/asset-hypotheses/benchmark-memory.mjs
```

The semantic flag uses macOS Swift and Apple's local English sentence embedding. The texture check requires `cwebp`, `ffmpeg` and `ffprobe`, and uses `sips` on macOS or `rsvg-convert` on Linux. To generate fresh layouts, start [llama-server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) with the Qwen2.5 1.5B Instruct Q4 K M GGUF at `127.0.0.1:18327`, then run the command below. One example is `llama-server -m /path/to/qwen.gguf --host 127.0.0.1 --port 18327 -c 4096`. The path is optional and can point to a temporary file if you want to compare model output without replacing the saved browser examples.

```sh
node hypothesis-non-production/test/asset-hypotheses/try-model.mjs /tmp/framebreak-new-layouts.json
```
